# 架构说明

## 请求链路

浏览器通过同源 `/api/v1` 访问后端。Nginx 提供前端静态文件，并代理 API、health 与 profile 端点。React 页面展示数据与发起操作，服务端负责认证、角色及学院范围检查、业务计算和持久化。

## 后端

`backend/app/api` 组织管理 API；`schemas` 定义接口数据契约；`services` 执行业务规则；`models` 定义 SQLAlchemy 模型；`alembic` 保存现存迁移。部分学生与企业门户代码位于 `app/d2`。路径名称保留原工程结构，不据此声明门户已完整交付。

数据库使用 PostgreSQL 与 pgvector。迁移、安装身份、数据档位和附件命名空间各有检查入口。新容器启动依次执行附件预检、数据库身份预检、迁移、安装身份确认、附件命名空间确认，再启动 API。

## 权限与配置

管理端包含管理员、就业办、辅导员和只读领导角色。辅导员的学院范围及写入权限由服务端检查。`APP_PROFILE` 表示数据档位，`DEPLOYMENT_MODE` 表示部署拓扑；案例默认使用 demo + local。数据库 URL 与 JWT 密钥显式提供，生产档位的独立字段密钥与安装身份守卫保留。

## 模型与规则

风险与匹配包含确定性业务计算；模型接口承担需要语言模型的部分。provider 单元测试仅验证调用或算法契约，不代表真实模型可用性或效果。本案例不附带模型权重，不默认下载模型，也不将模型不可用后的降级计作模型验收通过。

## 隔离

测试与演示分别生成随机项目名、数据库名、安装标识和凭据，分别使用自己的数据卷与内部网络。测试不映射宿主端口；演示前门绑定 `127.0.0.1:18090`。初次构建仍需下载依赖与镜像，内部网络约束不等于离线安装包。
